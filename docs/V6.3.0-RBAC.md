# GeDefense Linux V6.3.0 — Management-API RBAC (R6) and anti-truncate witness priority (S08/S15)

**Status:** implemented, tested offline on the WSL2 gate host (see the verification
section for the exact commands); live-lab items are marked `NOT_TESTED`.
**Scope:** `control/` (management API on loopback) and `gateway/` (public TLS
termination + operator session). No configuration-schema change is required: both
optional credentials are convention-based adjacent files.

## 1. Role model

The role is derived server-side from the presented credential. **No request header
is ever trusted as a role.** The ladder is ordered; a credential satisfies a
requirement when its role is `>=` the required role.

| Role | Credential | Permitted |
|---|---|---|
| `Observer` | optional `<dashboard.token_file>.observer` (0600) | `GET`/`HEAD` on every management route. No mutation of any kind. |
| `Operator` | the existing dashboard bearer token (unchanged) | every non-critical route, exactly as before this work package: policy, previews, apply/reverse, settings, lockdown, witness, scanner actions, … |
| `Critical-Unlock` | a fresh step-up proof (below) **in addition to** the Operator bearer | the destructive class only: quarantine prune, review acknowledgement, review deletion |

Absence of the optional observer file is an honest, documented state: the Observer
role is simply unavailable and the file grants nothing. The Operator token keeps
its rotation semantics (`currentToken()` re-reads and re-validates the token file
on every use); the observer credential is re-read and re-validated on **every**
request, so rotating or deleting it takes effect immediately without a restart.

### 1.1 Per-route matrix

All existing routes keep their exact registration, order and middleware. The role
check is applied inside `s.auth` (`control/rbac.go`), by method and by the curated
critical list:

| Route class | Examples | Minimum role |
|---|---|---|
| read-only (`GET`, `HEAD`) | `/api/v1/status`, `/api/v1/evidence`, `/api/v1/settings/*`, `/api/v1/xdr/review`, `/api/v1/witness/status`, `/metrics`, `/bootz`, `/panelz`, `/api/v1/stream` | `Observer` |
| ordinary mutation (`POST`, `PUT`, `DELETE`) | `/api/v1/settings/*`, `/api/v1/allowlist*`, `/api/v1/blocks*`, `/api/v1/lockdown/*`, `/api/v1/transactions/*`, `/api/v1/witness/*`, `/api/v1/release/*`, `/api/v1/system/restart`, scanner/apply routes | `Operator` |
| **critical (destructive)** | `POST /api/v1/quarantine/prune`, `POST /api/v1/xdr/review/{id}/ack`, `DELETE /api/v1/xdr/review/{id}` | `Critical-Unlock` |

The critical list is the single source of truth in
`control/rbac_types.go:criticalManagementAction`. The gateway mirrors it in
`gateway/rbac.go:gatewayCriticalRoute` and the two must be changed together (the
gateway refuses a step-up proof on a route it does not classify as critical, and
the control plane refuses the claim on a route it does). `PermitV1` upsert/removal,
a Chameleon reveal and an update override have **no HTTP route yet** in this tree;
they are the documented extension points and are classified critical when they
land.

### 1.2 Discovery and step-up routes (new, additive)

| Route | Auth | Purpose |
|---|---|---|
| `GET /api/v1/auth/roles` | Observer+ | honest role availability: which roles this process offers, the critical route list, the step-up contract lengths. Carries no credential material. |
| `POST /api/v1/auth/step-up` | Operator, direct loopback only | mints one short-lived direct step-up proof. Refused for gateway-proxied requests (`X-VGT-Gateway: direct-access-v2`), because a browser must re-authenticate its password at the gateway instead. |
| `POST /gateway/step-up` | authenticated operator session + exact public origin + password | re-verifies the operator password with the existing Argon2id verifier and returns one opaque, TTL-bounded, single-use proof. |

## 2. Step-up flows

Two mutually exclusive proof paths exist. A request that carries the gateway trust
marker (`X-VGT-Gateway: direct-access-v2`) may only use the gateway claim; a direct
request may only use the direct proof. A proof is never a credential of its own:
both are bounded to **at most five minutes**, single-purpose and single-use, and
both are verified server-side.

### 2.1 Direct loopback flow

1. Provision `<token_file>.critical` (see §4).
2. `POST /api/v1/auth/step-up` with the Operator bearer and
   `{"purpose":"critical"}` (plus the usual `X-VGT-Request-ID`).
3. The answer is `{"step_up":"critical|<expiry_unix>|<nonce>|<mac>", "purpose":"critical", "expires_at":"…", "ttl_seconds":120}`.
4. Present it once as `X-VGT-Step-Up-Proof: critical|<expiry>|<nonce>|<mac>` on
   exactly one critical request.

Verification (all checks server-side, constant-time MAC compare):

- shape `critical|<expiry_unix>|<nonce>|<hex-mac>`, nonce 16 random bytes as
  lowercase hex, MAC 32 bytes as lowercase hex;
- `now < expiry <= now + 5 min` (a leaked key cannot mint long-lived capability);
- `HMAC-SHA256(critical_key, "VGT-GEDEFENSE-CRITICAL-STEP-UP-V1\x00" + "critical|<expiry>|<nonce>")`;
- the nonce is claimed from a bounded single-use cache (4096 entries, TTL-bounded,
  oldest-entry eviction);
- peer is loopback.

The direct proof is **not a second factor** in the password sense: a process that
already holds the Operator bearer and can read the host's critical key file is by
definition host-root-equivalent. Its value is a bounded, single-purpose,
single-use capability for the most destructive actions, so a stolen browser
session or a script cannot perform them without a deliberate, expiring proof.

### 2.2 Browser flow (gateway)

1. The operator has an authenticated gateway session (password login, unchanged).
2. `POST /gateway/step-up` with the session cookie, the exact public `Origin` and
   `{"password":"…"}`. The password is verified through the existing Argon2id
   verifier and the existing KDF admission gate; it is never logged and never
   stored.
3. The answer is `{"step_up_proof":"<opaque>", "purpose":"critical", "expires_at":"…", "ttl_seconds":120}`.
   The proof is opaque, random, bound to that server-side session and single-use.
4. The browser sends it once as `X-VGT-Step-Up-Proof` on the critical request.
   The gateway consumes it (session-bound, TTL 120 s, single use), builds the role
   claim and forwards it; the proof header itself is never forwarded.
5. The control plane verifies the claim, applies the role and consumes the claim
   nonce.

Exact gateway claim contract (both components pin it with a test vector):

| Header | Value |
|---|---|
| `X-VGT-Role` | `critical` |
| `X-VGT-Step-Up` | `password:<nonce>` (nonce = 16 random bytes, lowercase hex) |
| `X-VGT-Claim-Ts` | decimal Unix seconds |
| `X-VGT-Claim-MAC` | lowercase hex HMAC-SHA256 |
| `X-VGT-Gateway` | `direct-access-v2` (path selector, not authority) |

```
message = "critical|password|<ts>|<nonce>"
MAC     = HMAC-SHA256(backend_token, "VGT-GEDEFENSE-GATEWAY-CRITICAL-CLAIM-V1\x00" + message)
```

The control plane accepts the claim only when: the peer is loopback, the gateway
marker is present, the role is `critical`, the method is `password`, the nonce is
well-formed, `|now − ts| <= 30 s`, the MAC verifies against the presented backend
credential, and the claim nonce has not been seen before (bounded replay cache,
TTL 90 s, 4096 entries). The proxy Director deletes every inbound
`X-VGT-Role`/`X-VGT-Step-Up`/`X-VGT-Claim-*`/`X-VGT-Step-Up-Proof` header before it
re-adds a verified claim, so a browser cannot forge one.

## 3. Brute-force lockout

Two bounded per-source guards (source = peer address; the tables hold at most 4096
sources, the oldest is evicted, failures are pruned by window):

- **Management-API credential guesses**: 5 failures inside 15 minutes →
  5-minute lockout, answered with `429` + `Retry-After`. The lockout is reported
  once as a bounded `rbac.lockout` info event (fingerprint, never an address,
  credential or path). A **valid credential is never locked out**: the operator can
  always reach the platform with the right token, which is the documented
  availability guarantee; the lockout bounds guessing, it is not a second factor.
  A successful authentication clears the source's failure history.
- **Critical step-up verification**: same 5/15 min → 5-min lockout for failed
  proofs or claims on a critical route. The attempt that reaches the threshold is
  still answered as a refusal; later attempts get `429`. A successful step-up
  clears the history.
- **Gateway password step-up**: its own 5 failures / 15 min → 5-minute per-source
  lockout (`429` + `Retry-After`), bounded proof and failure tables (256 proofs,
  4096 sources, oldest-entry eviction). The pre-existing sign-in lockout is
  unchanged (5 failures inside the 15-minute window refuse further sign-ins with
  `429` + `Retry-After: 900`).

Lockout events are one bounded event per transition; they never carry a secret.

## 4. Provisioning

`<token_file>` defaults to `/var/lib/vgt/gedefense/dashboard.token`. The optional
files are adjacent to it. Both must be regular, non-symlink files, mode `0600`,
owned by the control-plane account (`gedefense`) or root; the control plane
re-validates mode and ownership on every use and reports a bounded
`rbac.credential_rejected` event if the policy is violated.

```bash
# Observer (read-only) credential: 256 random bits, base64url, 43 characters.
umask 077
head -c 32 /dev/urandom | base64 | tr '+/' '-_' | tr -d '=' > /var/lib/vgt/gedefense/dashboard.token.observer
chown gedefense:gedefense /var/lib/vgt/gedefense/dashboard.token.observer
chmod 0600 /var/lib/vgt/gedefense/dashboard.token.observer

# Critical step-up key: at least 32 random bytes (raw). Provision only where the
# direct loopback step-up flow is actually wanted.
head -c 32 /dev/urandom > /var/lib/vgt/gedefense/dashboard.token.critical
chown gedefense:gedefense /var/lib/vgt/gedefense/dashboard.token.critical
chmod 0600 /var/lib/vgt/gedefense/dashboard.token.critical
```

Rotation/removal is a file operation: the next request re-reads the file, so
replacing or deleting an observer credential revokes it immediately (delete →
Observer unavailable; the Operator token is unaffected). Remove the critical key
file to make the direct critical path unavailable; a browser flow still works
through the gateway because it is keyed on the backend credential, not on this
file.

## 5. Anti-truncate witness priority (S08/S15)

`control/xdr.go` already calls `e.pushCriticalWitness(incident)` inside
`appendIncident` **before** the forensic log record is appended, and the finding's
evidence record was committed to the authenticated ledger first (evidence-first
rule). `control/witness_priority.go` fills that seam:

- **Trigger set** (flood protection): GIEF envelope `sbc_family == SBC-EVID-08`,
  rule IDs `XDR.SELF_TAMPER` / `XDR.SELF_ARTIFACT` / `WITNESS.EQUIVOCATION` /
  `BASELINE.HASH_MISMATCH`, or an evidence-integrity category (`integrity`,
  `evidence`, `self-tamper`, `witness`, `worker-integrity`). Severity alone and all
  other families are never pushed.
- **Delivery**: non-blocking hand-off into a bounded queue (64 records) drained by
  one long-lived worker per XDR engine (no goroutine per incident). The worker
  builds a signed `vgt-gedefense-witness-checkpoint-v1` checkpoint of the current
  authenticated ledger head (which already covers the finding's evidence record)
  and pushes it through the existing hardened witness HTTP client with a 6-second
  hard bound and retry-free profile.
- **Dedupe**: record hash first, then incident id, then a content hash; bounded
  table (4096 entries, 1-hour TTL, oldest-entry eviction).
- **Honesty**: witness disabled/offline → one bounded
  `xdr.witness_priority_unavailable` event (no incident, never a fake success);
  a push failure → counted, one bounded `xdr.witness_priority_failed` event per
  5-minute cooldown; queue overflow → counted and one bounded
  `xdr.witness_priority_dropped` event. The hook isolates panics and never fails
  the XDR ingest path.
- **Requirement for S08/S15 ROBUST**: the out-of-band witness namespace must be
  enabled (`witness.enabled = true`, `witness.mode = "http"`, pinned transport
  anchor, reachable witness). A fully local host with the witness disabled can
  still truncate its local log; the platform reports that fact instead of claiming
  anti-truncation.

## 6. Residual limits and integration gaps

1. **Witness requirement**: S08/S15 anti-truncation is only ROBUST with the
   witness enabled. With the witness disabled the hook reports
   `xdr.witness_priority_unavailable` and the deployment has no out-of-band copy.
2. **Asynchronous push window**: the hand-off is synchronous and before the log
   write, but the actual network push is asynchronous. A truncation in the
   milliseconds between the log append and the witness acknowledgement can still
   race the push; the signed checkpoint it carries is what limits the damage.
3. **Direct step-up is host-root-equivalent** (§2.1): it is a bounded capability,
   not a second authentication factor.
4. **Gateway claim key = backend token**: the browser cannot forge the claim
   (it never sees the backend token and the proxy strips claim headers), but a
   local process that holds the Operator/backend token can mint an equivalent
   claim. The direct `.critical` key is the stronger host-side control. A
   dedicated gateway/control shared secret would require an existing key-file path
   that the gateway can already read; none is wired today, so this is documented
   rather than invented.
5. **No configuration-schema change**: the observer credential and the critical
   key are convention-based adjacent files. A future operator-facing setting
   would be a separate change; the `GET /api/v1/auth/roles` surface already names
   availability honestly.
6. **PermitV1 upsert/removal, Chameleon reveal, update override** have no HTTP
   route in this tree yet; they are classified critical when they land, in
   `control/rbac_types.go` and `gateway/rbac.go` together.
7. **Gateway route list coupling**: the gateway's critical-route classifier is a
   mirrored list; it is regression-tested on both sides. A new critical route must
   be added to both.
8. `WITNESS.EQUIVOCATION` incidents created by the witness engine itself go
   through `state.AddIncident`, not `appendIncident`, so the priority hook does
   not loop back into the witness path.
9. Live-lab items `NOT_TESTED` on this host: real gateway↔control browser step-up
   over the packaged TLS topology, a real external witness server
   acknowledgement, and the packaged file ownership (root/gedefense) — the code
   paths are covered by offline tests with real temporary files, fake transports
   and an in-process TLS gateway.
10. The single-use nonce/proof caches are in memory by design (no disk writes on
    the authentication path). A process restart forgets used nonces, so a proof
    that is still inside its TTL can in principle be replayed once across a
    restart; the window is bounded by the TTL (≤ 2 minutes) and a proof only ever
    unlocks one critical action.
