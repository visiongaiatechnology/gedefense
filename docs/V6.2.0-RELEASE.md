# GeDefense Linux V6.2.0 — Defense Maximization & Telemetry Resilience

**Release date:** 2026-11-21 (Europe/Berlin)  
**Base:** GeDefense Linux `6.1.2` (`main@33355bc`, dirty worktree)  
**Product version:** `6.2.0` (`VERSION`, Control, Gateway, Rust workspace, AstraeaOS contract, Arch PKGBUILD, OneClick header)  
**Scope:** HardRed evidence review `GEDEFENSE_6.1.2_OPTIMIZATION_AND_DEFENSE_MAXIMIZATION.md` plus the StyX `FLOW_EVENTS` telemetry follow-up.

## 1. What changed

### Malware and artifacts
- Asynchronous `FAN_CLOSE_WRITE` on-write sensor for `/tmp`, `/var/tmp`, `/dev/shm`, `/var/www` (configurable via repeated `--on-write-watch-root=`), with a bounded queue, ≤64 MiB full scans, ≤1 MiB signature probes, SHA-256 re-check under the quarantine lock, and encrypted quarantine.
- Host tmp visibility: `gedefense-core.service` uses `PrivateTmp=false` plus explicit read/write grants for exactly the four drop roots; `/home` and `/opt` stay read-only.
- Bounded recursive ZIP/GZIP/TAR inspection: depth 8, entry ≤16 MiB, total ≤64 MiB, ≤10 000 entries, 200:1 ratio; zip-slip/absolute/backslash paths fail closed; malformed members are never silently accepted.
- HTTP raw-body Airlock for `application/octet-stream`/unknown `POST`/`PUT` bodies (EICAR/webshell markers, score 110, HTTP 403), independent of multipart uploads.

### Endpoint containment
- TITAN Exec global mode `4` (`untrusted`): blocks untrusted exec paths by owner, world-writable/sticky path and dentry ancestry; per-cgroup scopes remain `0..3`. ABI-2 offsets: filename, inode owner, file dentry, dentry parent/inode/size; reasons 11–13.
- `XDR_KILL_TREE`, `XDR_GROUP_STOP`, `XDR_GROUP_CONT`: bounded `/proc` DFS (≤4096 processes, depth 64, ≤1024 signals), PPID + PGID scope, identity checks before/after `pidfd_open`, `pidfd_send_signal`, hard protection allowlist (PID 1–4, systemd/sshd/gedefense/kernel threads).
- Kernel ransomware sensor: `vfs_write`/`vfs_rename`/`vfs_unlink` kprobes, per-TGID tracker, integer-only entropy, entropy-burst (≥15 distinct inodes/500 ms) and rename-storm (≥25 rename+unlink/250 ms) signals; the core resolves the real PGID and freezes the whole group with reversible `SIGSTOP`; trusted package/compiler comms are skipped. Control records evidence first, then either escalates with `KILL_TREE` (enforce mode) or releases with `GROUP_CONT`.
- Credential guard: `file_open` BPF-LSM for `/etc/shadow`, `/etc/gshadow` and bound secret files; only allowlisted auth/system comms may read; `-EACCES` plus `CRED_GUARD` event. `active` is only reported when armed+attached+files>0; unarmed/unattached never blocks login/PAM.

### StyX and flow telemetry
- `cgroup_path` in StyX cell modes and allow rules; cgroup2 inode resolver on every sync; legacy numeric IDs remain supported; restart/reboot drift is re-applied atomically and unresolved paths become `degraded` (no silent fail-open).
- `FLOW_EVENTS`: 16 MiB ring, core drain 64 events/poll (was 8), 16 KiB text payload, control parser 64/16 KiB/64 KiB response bound. egress enforcement path unchanged.
- Telemetry status separates `enforcement_active` from `telemetry_state` (`healthy/degraded/stale/unavailable/disabled`) and exposes emitted/dropped deltas, drop ratio and drain lag; dashboard/overview show “telemetry degraded” rather than an unqualified “active”.

### WAF / edge
- SQL comment/whitespace canonicalization, schema-probe/comment-obfuscation rules, scanner recon/user-agent rules, semicolon-chained query/form handling, secret-config probe (`/.env`, `.git/config`, `wp-config.php.bak`) at score 95, raw-body malware detection, bounded 780 KB–1.5 MB fast-pass, deterministic `429` + `Retry-After`.

### Hardening, context and packaging
- CIS/Lynis M5.1 sysctl catalog (21 controls), profiles `linux-server-balanced`, `astraeaos-workstation-strict`, `astraeaos-cis-l1`, transactional preview/apply/verify/reverse; opt-in `gedefense-cis-baseline` script for SSHD drop-in, UMASK, legal banner, module blacklist and auditd baseline. No silent live SSHD/PAM change.
- Kinetic→XDR M5.2: `kinetic.block_applied` incidents resolve local service/port from `/proc/net/*`, attach MITRE technique and create an `AttackStoryNode` with `has_lineage_or_chain=true`.
- M2.4 credential guard is implemented; distributed canaries into real data roots are deliberately **not** enabled in 6.2.0 (the existing privileged canary root/broker is unchanged; a real-data-root deployer needs its own fd-anchored broker and write grants).
- Version bumped to `6.2.0`; README badges/links, CHANGELOG, RELEASE-NOTES, AstraeaOS contract capabilities and Arch PKGBUILD updated.

## 1a. Audit follow-up fixes (2026-11-22)

A post-build source audit found four release-blocking defects; all four were fixed before the final build:

1. **On-write UID blindness:** `classify_write()` rejected every `owner_uid != 0` file, so www-data/pentest-user drops into `/tmp` and `/var/www` were invisible. The ownership filter is gone; executable drops are fully scanned and non-executable files are probed up to 16 MiB (was 1 MiB), while the watch-root and fd-anchored quarantine boundary remain.
2. **Persistent hardening mismatch:** the Rust core knew only the two old profiles and a 10-bit mask. It now understands `astraeaos-cis-l1`, the full 21-bit custom mask and all new CIS keys; balanced/strict content was aligned with the Go catalogue and legacy 6.1 files remain recognized for upgrade. The core unit grants the new `/proc/sys` paths explicitly.
3. **Ransomware freeze latency/arming:** the core arms as soon as at least one kprobe is attached; the drain cadence is 100 ms instead of one second, so the control-plane round trip no longer adds a full second to the kernel-triggered `SIGSTOP`.
4. **Credential-guard false lockout:** local `login`, cron and account/group-management binaries were missing from the allowlist and could receive `EACCES` on `/etc/shadow` during package upgrades or console login. The allowlist was extended accordingly.

## 2. Security invariants preserved

- No benchmark payload/test string is hard-coded; the changes close attack classes.
- No silent enforcement bypass: StyX failures are `degraded`, TITAN only claims `active` after attach, credential guard stays pass-through until armed+attached.
- Fail-closed boundaries: unsigned/unverified exec policy still refuses strict compile; archive decode failures reject; credential guard is pass-through only when not ready.
- Reversible containment: ransomware group freeze is `SIGSTOP`, releasable with `GROUP_CONT`; failed release is a critical operator event.
- No new external runtime/CDN dependency; the archive decoders and signature matching are local Rust code.

## 4. Migration / rollback

- Upgrade from `6.1.2` replaces the signed `gedefense-core`/eBPF object and control binary; the eBPF object must be loaded by the new core. A rolling back to the old binaries requires restoring the old object and restarting all units.
- `PrivateTmp=false` is a deliberate functional change for on-write visibility; verify host tmp paths are not on a mount the service user cannot traverse.
- New StyX `cgroup_path` fields are additive; legacy numeric IDs continue to work. No schema migration is required for existing settings.
- The CIS baseline is opt-in and supports `--remove`; no SSHD/PAM change is applied by default.
- Ransom/credential sensors are best-effort: missing kernel capabilities result in status `attached=0`/`active=0`, not a false enforcement claim.

## 5. Known limitations / honest gaps

- YARA/`yara-x` rule packs are not bundled; the on-write/HTTP scanner uses the existing signed hash feed plus bounded EICAR/webshell byte markers. A full YARA engine remains a future enhancement.
- M4.5 is limited to deterministic `429` handling and the large-body fast-pass; the L7 buffer pool and one-hop optimization are not part of this release.
- M2.4 distributed real-data-root canaries remain out of scope; only the existing privileged canary root is active.
- M3.3 automatic "web-worker egress only loopback/DNS" defaults are **not auto-enabled**. Enforcing that without an explicit backend/API allowlist would break WordPress updates, payment/SMTP and external APIs; the symbolic StyX path/mode machinery is in place, but the final default policy requires an operator-specific allowlist.
- The optional `/tmp noexec,nosuid,nodev` provisioning variant from M2.1 is not forced by this release; it remains an operator hardening decision because some package/build workflows rely on exec from tmp.
- The Web UI does not yet render dedicated `ransom_sensor`/`credential_guard` panels; the API, overview and hardening settings expose the status/details.
- Canary distribution is opt-in and not enabled by default; real data roots are not seeded automatically.
- No signed OneClick `.run` artifact was generated in this workspace; release signing, SBOM and target-host qualification remain release-CI gates.
- Several pre-existing monolithic files remain above 500 lines; new 6.2 modules are split and bounded, but a full monolith split is intentionally out of this patch's scope.
