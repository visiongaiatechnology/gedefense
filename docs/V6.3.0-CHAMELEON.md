# GeDefense Linux V6.3.0 — Chameleon Identity Mode (AP-8)

Status: **IMPLEMENTED_NOT_VERIFIED** for the live kernel path (the patched object
is exercised by an ignored real-object test that runs `aya::Ebpf::load` on a real
eBPF object; live attach and a production systemd host are NOT_TESTED on this
workstation). Default-off is fully verified: with no manifest every byte, name,
path and port is the documented public GeDefense identity.

## 1. What Chameleon is — and what it is not

Chameleon is an **opt-in install/hardening profile**, decided once by the
installer, not a runtime self-mutation:

* The installer writes a small, root-owned install manifest with a random
  per-installation salt and the neutral socket/port/state layout.
* At startup the privileged Rust core patches the in-memory eBPF object once,
  before the maps/programs are loaded, so the kernel sees installation-specific
  program/map identifiers.
* The control plane reads the same manifest once and applies the neutral socket,
  loopback port and daemon state roots to its configuration.
* The signed local VGT admin audit keeps the real mapping. The administrator can
  always recover it; unprivileged reconnaissance cannot find it.

There is **no runtime rename, no self-modification and no toggle**: a running
installation either has a manifest (neutral identity) or it does not (public
identity). The default (`--chameleon-manifest=""`, no file) is byte-identical to
the 6.2 public identity.

Why not rename at runtime: runtime mutation would break `fs-verity`/IMA
measurement of the binary, the systemd unit contract and the admin
accountability chain. The install profile avoids all three.

## 2. Threat model

In scope:

* **Anti-recon against user-space checkers.** A local or remote reconnaissance
  tool that lists kernel objects must not learn that GeDefense is installed from
  the kernel object names: `bpftool prog list`, `bpftool map list`, `/proc/*`
  tooling and `/sys/fs/bpf` listings no longer show `gedefense`, `styx`, `titan`,
  `vgt`, `cred_guard` or `lockdown` markers in the managed identifiers.
* **Anti-recon against socket/port probes.** Core IPC and scan sockets and the
  loopback dashboard backend port are installation-specific. The public HTTPS
  port is installation-specific as well (renderer supplied).
* **Admin accountability.** The real `public=neutral` mapping is written to a
  root-only audit file under the neutral state root and committed (hash only) to
  the signed evidence ledger. The install manifest with the salt is the recovery
  anchor.

Out of scope / not claimed:

* Protection against a root-level attacker who can read the manifest or the
  audit file.
* Hiding the vendor/company from the binary on disk, from systemd unit names, or
  from the process command line. The binary path
  `/opt/vgt/gedefense/current/...` and the unit descriptions still contain the
  vendor name. Renaming those requires installer-level unit/binary relocation
  and is listed as a residual limit (§8).
* Any encryption or obfuscation of the eBPF object; the on-disk object is not
  modified by this feature.

## 3. Manifest format (strict, bounded, rejecting)

Path: chosen by the installer, by convention
`/etc/<neutral-vendor>/<install-id>.conf`, mode `0640 root:gedefense`. It is
read by the privileged core (root) and by the unprivileged control plane
(`gedefense` group); it must not be readable by any other local account because
it carries the HMAC salt for the neutral names. A literal `root:root 0640`
manifest would make the unprivileged control plane unable to read the identity it
must apply, so the shipped default group is the platform service group.

The parser in `rust/gedefense-core/src/chameleon.rs` and
`control/chameleon.go` is strict and identical on both sides:

* maximum 16 KiB, UTF-8, LF line endings, no BOM, no control characters;
* first line exactly `vgt-gedefense-chameleon-v1`;
* then `key=value` lines: no duplicate keys, no unknown keys, no empty values;
* a present-but-invalid manifest is **fatal at startup** — an operator who asked
  for Chameleon can never silently get the public identity;
* the file must be a regular non-symlink file, not group/world writable, owned by
  root or by the effective user (euid 0 or file uid).

Required keys:

| Key | Rule |
|---|---|
| `install_id` | 16–64 chars `[a-z0-9-]`, no leading/trailing `-` |
| `bpf_name_salt` | exactly 64 lowercase hex = 32 random bytes (HMAC salt) |
| `core_socket` | absolute normalized path (`/run/...` in practice) |
| `scan_socket` | absolute normalized path (`/run/...`; parent jail see §8) |
| `bpf_pin_root` | absolute normalized path below `/sys/fs/bpf` |
| `state_dir` | absolute normalized daemon state root (e.g. `/var/lib/...`) |
| `config_dir` | absolute normalized install identity root (e.g. `/etc/...`) |
| `public_port` | 1024–65535 |
| `backend_port` | 1024–65535, distinct from `public_port` |
| `neutral_unit_prefix` | `[a-z][a-z0-9-]{2,20}` |

Optional: `admin_audit_path` (absolute normalized path of the admin mapping
audit file; default `<state_dir>/chameleon-map.audit`).

`core_socket` and `scan_socket`, `state_dir` and `config_dir`, and both ports
must differ. Paths must be canonical: no `//`, no `.`/`..`, no trailing `/`,
not `/`.

## 4. Install flow

A new installation that opts in runs the helper before the services start:

```bash
sudo bash scripts/apply-chameleon-profile.sh \
  --install-id="$(openssl rand -hex 8 | sed 's/^/gdn-/')" \
  --state-dir=/var/lib/gdn/state \
  --config-dir=/etc/gdn \
  --core-socket=/run/gdn/core.sock \
  --scan-socket=/run/gedefense-scan/gdn-4f8c.sock \
  --bpf-pin-root=/sys/fs/bpf/gdn \
  --backend-port=31441 --public-port=31440 \
  --unit-prefix=gdn
```

The helper is idempotent and validates every value (`bash -n` clean, unit smoke
test `packaging/tests/install-chameleon-smoke.sh`). It never writes outside the
directories it is given plus the systemd/tmpfiles drop-in directories of the
target root, and never touches keys, TLS material or packaged units. Without
`--salt` it reads 32 bytes from `/dev/urandom`; the salt must then be treated as
an installation secret and must not be published.

It writes:

1. the manifest (`0640 root:gedefense`, atomic replace);
2. `/etc/systemd/system/gedefense-core.service.d/10-chameleon.conf` — resets
   `RuntimeDirectory=`, adds the neutral runtime dir, rewrites `ExecStart=` with
   `--chameleon-manifest=`, `--bpf-pin-root=`, neutral `--socket=` and
   `--scan-socket=` (the old identity-bearing flags are **removed**, because the
   core's argument parser takes the first occurrence), and adds exact
   `ReadWritePaths=` grants for the neutral state/runtime/scan roots;
3. `/etc/systemd/system/gedefense-control.service.d/10-chameleon.conf` — passes
   the same manifest to the unprivileged control plane and grants only the
   neutral state root for writes;
4. `/etc/systemd/system/gedefense-access.service.d/10-chameleon.conf` (when the
   gateway unit exists) — rewrites only `--backend=http://127.0.0.1:<port>` and
   `--listen=<host>:<public-port>`; TLS, account separation and the gateway
   sandbox are untouched;
5. `/etc/tmpfiles.d/10-chameleon-neutral.conf` — provisions the neutral runtime,
   state, config and scan roots with the platform service group;
6. applies `systemd-tmpfiles --create` and `systemctl daemon-reload` (real root
   only).

`scripts/oneclick-installer-header.sh` is **not** wired to call the helper in
this change; see §8 for the precise integration point and why editing the live
one-click flow was avoided.

## 5. What is renamed — kernel-visible

Only the managed program/map namespace of the shipped eBPF object:

* program symbols starting with `gedefense_`;
* map symbols starting with `ALLOWLIST_`, `BLOCKLIST_`, `BPF_GUARD_`, `CELL_`,
  `CRED_GUARD_`, `CROSS_VIEW_`, `DNS_CAPTURE_`, `EGRESS_`, `EXEC_`, `FLOW_`,
  `FLOW_AGG_`, `INGRESS_`, `KERNEL_HOOK_`, `KERNEL_PROBE_`, `LOCKDOWN_`,
  `MALWARE_`, `PACKET_`, `PENDING_`, `PERSIST_`, `RANSOM_`, `SEC_CRIT_`,
  `STYX_`, `TELEMETRY_`, `TITAN_`, `TRUSTED_EXEC_`, `WORKER_`.

Derivation (`rust/gedefense-core/src/chameleon.rs`):

* `HMAC-SHA256(salt, domain || public_name || counter || block)` with domain
  `map:`/`prog:`, mapped onto `[a-z0-9_]`, first character a lowercase letter;
* **same byte length** as the public name;
* collisions are retried with a counter inside the HMAC input (max 128), never
  resolved silently to the public name; forbidden substrings `gedefense`, `vgt`,
  `styx`, `titan`, `geodefense` are retried as well;
* every neutral name is unique across the object and never equals a public
  identifier.

ELF patcher (`ChameleonProfile::load_object`):

1. reads the object bounded (≤16 MiB), regular non-symlink file;
2. parses the ELF64 LE section table, the symbol string table (`.strtab`, which
   bpf-linker merges with `.shstrtab`) and the symbol tables (`.symtab`);
3. discovers every managed symbol spelling and builds the plan;
4. **appends** the neutral names to the string table and repoints exactly the
   managed symbol entries (`st_name`), then zeroes the now-unreferenced public
   bytes except for section names and unmanaged symbol names, and shifts the
   trailing section data/section header table by one constant delta;
5. rejects (fatal) an object with no managed identifiers, a managed section
   name, a `.BTF` section (this build only supports the shipped BTF-less object),
   or any residual managed symbol name after the rewrite;
6. writes `<state_dir>/chameleon-map.audit` (0600, atomic, bounded) and loads the
   patched bytes with `aya::Ebpf::load(&bytes)`.

Why append instead of in-place same-length overwrite: the shipped object's
string table suffix-merges strings. The section name `xdp` is a suffix of the
program symbol `gedefense_xdp`, and `EXEC_EVENTS` is a suffix of
`TITAN_EXEC_EVENTS`. An in-place rewrite would corrupt a section name that aya
needs to select program types, so the patcher appends and repoints instead. The
name-length invariant is preserved regardless.

Evidence (real object `rust/target/bpfel-unknown-none/release/gedefense-ebpf`,
471 400 B, built with nightly-2026-07-16, WSL2 root):

```
chameleon object smoke: 174 symbols renamed, 3741 neutral bytes appended
chameleon object smoke: aya parsed the patched object (44 programs, 132 maps)
```

with assertions that every section name and every non-symbol section payload is
byte-identical, no managed symbol resolves to a public name, and no managed
identifier survives as a string-table entry.

## 6. What is renamed — control plane and paths

`control/chameleon.go` `Apply(cfg Config) Config` overrides only
installation-specific, daemon-owned fields:

| Config field | Neutral value |
|---|---|
| `Core.Socket` | manifest `core_socket` |
| `Dashboard.Listen` | `127.0.0.1:<backend_port>` (loopback-only stays enforced) |
| `Policy.StateFile` | `<state_dir>/policy.json` (also relocates the evidence dir) |
| `XDR.IncidentLog` | `<state_dir>/incidents.jsonl` |
| `XDR.BehaviorProfileFile` | `<state_dir>/behavior-profiles.json` |
| `Runtime.SettingsFile` | `<state_dir>/runtime-settings.json` |
| `Release.EmergencyStopFile` | `<state_dir>/EMERGENCY_STOP` |
| `Feeds.ManifestPath` / `Feeds.SnapshotDir` | neutral state-dir paths |

Never changed by the profile: `Dashboard.AllowedHosts` (loopback list stays),
auth/TLS settings, the dashboard token file, policy/feed signing keys, the
storage master key, the runtime settings key and any enforcement/feature toggle.
`UserMalwareScan` keeps its packaged peer-bound path; an opted-in installation
uses `chameleonUserMalwareScan` (manifest-owned runtime socket, same bounded
`VGTSCAN1` protocol; authentication stays on the core side with `SO_PEERCRED`).

## 7. Audit mapping and recovery

* `<state_dir>/chameleon-map.audit` is written by the privileged core:
  `0600 root`, header `install_id`, `salt_fingerprint` (SHA-256 of the salt
  bytes, never the salt), `mapping_sha256`, then one `public=neutral` line per
  renamed identifier, sorted. It is atomically replaced and bounded (≤256 KiB).
* The control plane records **one** evidence-ledger entry at startup:
  `kind=chameleon.profile.active`, `source=chameleon`, target = mapping
  commitment hash (SHA-256 over install id + salt fingerprint + schema). No
  secret, no full mapping enters the signed ledger.
* Recovery: the administrator (root) reads the manifest and the audit file. The
  mapping is reproducible from the salt and the public name list at any time;
  the salt is the only secret needed. If the audit file or state root is lost,
  the manifest alone is sufficient: re-run the core with the same object and the
  same salt, or re-derive the names with the documented HMAC construction.
* Do not copy the manifest, audit file or `bpf_name_salt` into tickets, logs or
  support bundles. They are installation secrets.

## 8. Residual limits and integration gaps (honest list)

1. **Kernel names are truncated by the kernel itself.** `BPF_OBJ_NAME_LEN` is 16
   bytes; long public and neutral identifiers are truncated identically, so this
   change preserves existing behaviour, but it also means very long identifiers
   are not fully visible anywhere.
2. **Process/binary identity is not renamed.** `/proc/<pid>/comm` still says
   `gedefense-core`, the binary path is `/opt/vgt/gedefense/current/...`, the
   systemd units keep their packaged names and descriptions, and the config file
   stays at `/etc/vgt/gedefense/gedefense.toml`. Full neutral unit/binary
   renaming is an installer-level unit-generation task (copy units under neutral
   names plus `Alias=` in a way that cannot double-start); this change
   deliberately does not copy units (double-start risk) and only prints
   `<unit-prefix>-core` as an informational alias.
3. **Scan-socket parent jail.** The shipped core's `main.rs` (AP-8 ownership
   limit: only name-resolution edits were allowed there) enforces that the user
   scan socket's parent is exactly `/run/gedefense-scan`; the control-side
   packaged `UserMalwareScan` also pins the public scan socket path. The helper
   therefore requires the neutral scan socket below `/run/gedefense-scan`
   (filename neutral only) and refuses a foreign parent unless
   `--allow-foreign-scan-dir` is passed together with a matching core-side
   change. Moving the whole scan directory requires the core jail to take the
   parent from the manifest.
4. **Config/log/token paths outside the neutral state root.** The dashboard
   token (read by the gateway), TLS material, the policy/feed signing keys, the
   storage master key, the runtime settings key, the XDR baseline file and the
   `gedefense.toml` itself remain at their provisioned public paths. Moving the
   runtime settings key would make the settings store fail closed on an existing
   installation (it requires an existing key file), so only the settings document
   moves.
5. **`.BTF`-bearing objects fail closed.** The shipped bpf-linker object has no
   `.BTF` section. If a future build adds one, the patcher refuses (fatal) rather
   than risk corrupting BTF type references that aya needs; extending the
   patcher to BTF name tables is follow-up work.
6. **Mangled Rust helper symbols can still contain vendor text on disk.** The
   eBPF object's `.text` helper functions carry Rust-v0-mangled symbol names
   that embed module/function text such as `gedefense_ebpf` and, for some
   helpers, a public identifier as a substring. They are **not** program/map
   identifiers and never reach `bpftool`/kallsyms; per the "never touch
   non-matching strings" rule the patcher leaves them alone. The kernel-visible
   identifier set (the aya program/map keys) is verified to be neutral.
7. **`sec_crit.rs` (AP-9) currently does not resolve maps through the Chameleon
   profile.** It now takes `SEC_CRIT_EVENTS`/`SEC_CRIT_STATE`/`SEC_CRIT_COUNTERS`,
   `TELEMETRY_FLOOD_*` and `BPF_GUARD_STATE` directly. With a manifest active
   those maps are renamed in the kernel, so the lookup fails and the core exits
   fatally (never a silent public identity). The AP-9 owner must wrap those
   lookups in `chameleon::map_name(...)` / `chameleon::program_name(...)` like
   every other module before the combined AP-8 + AP-9 profile can be enabled.
   This is tracked as an integration note.
8. **One-click installer integration is not wired.** The helper is standalone and
   smoke-tested; the one-click header was not modified because it is a
   release-critical flow owned by other work packages and a half-integrated call
   could break clean installs. The exact integration point is after
   `install_units`/before `verify_units` in `scripts/oneclick-installer-header.sh`,
   with arguments derived from the operator's install profile.
9. **Live verification status.** The patched object parses with aya on WSL2 as
   root (44 programs, 127 maps) and every unit test passes, but no production
   systemd host, kernel attach or `bpftool` output was exercised in this
   workstation run. Treat live kernel behaviour as NOT_TESTED until a lab run.

## 9. Verification commands (AP-8 gates)

```bash
# Rust core/common typecheck for the static musl target
cd rust && cargo check --target x86_64-unknown-linux-musl \
  -p gedefense-common -p gedefense-core --locked

# eBPF crate typecheck (verifier still only in CI/lab)
cd rust && cargo +nightly-2026-07-16 check -p gedefense-ebpf \
  --target bpfel-unknown-none -Z build-std=core --locked

# Rust unit tests (pinned 1.97.1, WSL2 Ubuntu 24.04)
cd rust && cargo +1.97.1 test --locked -p gedefense-common -p gedefense-core

# Real-object patcher smoke (needs an eBPF object; root run additionally asks
# aya to parse the patched object)
cd rust && VGT_CHAMELEON_TEST_OBJECT=../dist/gedefense-ebpf \
  cargo +1.97.1 test --locked -p gedefense-core chameleon_real_object -- --ignored --nocapture

# Go gates
cd control && gofmt -l . && GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go vet ./...
cd control && CGO_ENABLED=0 go test -count=1 -run TestChameleon .

# Installer helper
bash -n scripts/apply-chameleon-profile.sh
bash packaging/tests/install-chameleon-smoke.sh

# Repository security regression audit (unchanged, must stay green)
bash ./scripts/security-audit.sh
```

The manifest template used by the helper lives at
`packaging/templates/chameleon-manifest.example` (placeholder values; generate a
real one with the helper, never ship the example salt).
