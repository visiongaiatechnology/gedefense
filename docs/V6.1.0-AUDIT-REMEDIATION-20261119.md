Scope: the five confirmed findings of the 2026-11-19 quick-profile security
audit against the GeDefense Linux 6.1.0 source tree.

Go 1.27.4, Rust 1.97.1). Unresolved `needs_validation` leads and the

## Residual risks

- FIND-001: the x32 ABI is intentionally unusable inside parser cells;
  classic BPF still cannot inspect `sockaddr` (pre-existing, documented).
- FIND-003: the kernel word is lock-free and guarded by epoch + read-back, not
  transactional; a concurrent TRIGGER race is detected and biased fail-secure.
- FIND-004: a device whose interface sysfs entries are not yet populated at
  device-add is classified Block; later interface uevents only de-authorize a
  parent, so an unluckily-timed genuine console stays blocked until an explicit
  USB phase release/CLEAR/re-arm. Genuine enumerated consoles/hubs stay allowed.
- FIND-002: the peer set stops inserting at 4096 and the ALPN map aggregates
  overflow; both are deliberate bounds, not silent eviction.
- FIND-005: the gateway still has no auth bypass; the finding was a rate-bucket
  collapse/header-integrity issue, now closed at the Director boundary.

## 6. Follow-up: Kernel 7.3 BTF v1 extended header

Not a finding of this audit, but the same target tree rejected a 32-byte BTF v1
header (`hdr_len == 24` hard check in `btf_offsets.rs`) even though the BTF v1
specification allows header extensions and kernel 7.3 uses a 32-byte header.
`aya-obj 0.3.0` (`Btf::parse`) accepts any `hdr_len >= 24` and uses it as the
section base, so the eBPF loader itself was already compatible.

Fix in `rust/gedefense-core/src/btf_offsets.rs`:

- `version == 1` remains mandatory;
- `hdr_len` is accepted when `24 <= hdr_len <= data.len()`; shorter headers,
  `hdr_len == 0`, and headers beyond the image stay fail-closed;
- `type_start`/`str_start` use `hdr_len.checked_add(offset)` (no unchecked
  addition), so the extension bytes are skipped correctly and overflow is an
  error;
- `hdr_len` is **not** assumed to equal the on-disk fixed prefix: the parser
  reads the extension area as part of the header, as the specification requires.

Regression tests in `rust/gedefense-core/src/main.rs`:

- `titan_btf_accepts_extended_v1_header`: inserts 8 extension bytes, sets
  `hdr_len = 32`, and asserts the resolved inode/file/bprm/mmap offsets match
  the 24-byte fixture exactly;
- `titan_btf_rejects_broken_headers_truncation_and_implausible_layouts` adds an
  `hdr_len > data.len()` rejection case alongside the existing 23-byte
  oversize/undersize checks.

Linux verification: `cargo +1.97.1 test --locked -p gedefense-common -p
gedefense-core -p gedefense-cell-helper` → exit 0 (core 121 tests, common 43,
cell-helper 41); `cargo +1.97.1 build --locked -p gedefense-core --release` →
exit 0; `scripts/security-audit.sh` → PASS.
